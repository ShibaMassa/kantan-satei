# 中古戸建て かんたん相場査定ツール 要件定義書

## 0. このドキュメントの位置づけ
Claude Codeが実装するための要件定義。実装中に判断に迷った場合は、本書の「目的」と「設計原則」を優先し、判断内容を `docs/decisions.md` に記録すること。

---

## 1. 目的
- **反響獲得**：Webサイト訪問者（売却検討者）に、中古戸建ての概算価格レンジを即時に提示し、「担当者による無料の精密査定」フォームへ誘導する。
- **KPI**：結果表示率（入力開始 → 結果表示）、CTAクリック率（結果表示 → 精密査定フォーム遷移）。

## 2. 設計原則
1. **ランニングコストゼロ**：有料API、有料ホスティング、LLM APIの実行時呼び出しは使わない。
2. **実行時に外部APIを呼ばない**：不動産情報ライブラリAPIはバッチ処理でのみ呼ぶ。ユーザーのアクセス時は、事前計算した静的JSONだけで査定する。これにより、APIキーの漏洩リスク、APIの利用制限、表示速度の問題を同時に解消する。
3. **データで説明できない数字は出さない**：件数不足の場合は価格を表示せず、精密査定へ誘導する。
4. **個人情報を扱わない**：本ツールは物件情報のみを入力として受け取る。氏名・連絡先は既存の査定フォーム側で扱う。

## 4. システム構成

```
[バッチ（ローカル or GitHub Actions、四半期ごと）]
  不動産情報ライブラリAPI (XIT001)
     ↓ 取得・クレンジング
  data/raw/*.json（※リポジトリにコミットしない）
     ↓ 集計・モデル推定
  public/model.json（町名別の土地単価・補正係数・誤差分布など、集計値のみ）

[フロント（Netlify無料枠・静的サイト）]
  入力フォーム → model.json で計算 → 価格レンジを表示 → 既存の査定フォームへ遷移
```

- 言語：バッチはPython 3.11以上、フロントは素のHTML/CSS/JavaScript（ビルド不要）を推奨。
- APIキーは `.env`（ローカル）とGitHub Actions Secretsでのみ管理する。`.gitignore` に必ず追加すること。
- 公開する `model.json` には集計値のみを含め、個別取引の生データは公開しない。

## 5. データ取得仕様
- エンドポイント：`https://www.reinfolib.mlit.go.jp/ex-api/external/XIT001`
- 認証：HTTPリクエストヘッダーにサブスクリプションキーを付与する。**ヘッダー名・パラメータ・レスポンスのフィールド名は、実装前に公式のAPI操作説明（https://www.reinfolib.mlit.go.jp/help/apiManual/xit001/）で必ず確認すること。推測で実装しない。**
- 主なパラメータ：`year`（必須）、`quarter`、`city`、`priceClassification`（01：取引価格、02：成約価格、未指定：両方）
- レスポンスはgzipエンコードされている場合があるので、デコード処理を入れる。
- 取得期間：成約価格は2021年以降のみ指定可能なので、**2021年第1四半期〜最新の四半期**を基本とする。取引価格は件数が不足する場合に限り、さらに過去にさかのぼる選択肢を残す（設定値で切り替え）。
- リクエスト間に待機時間を入れ、リトライ（指数バックオフ）を実装する。
- 取得結果はキャッシュし、再実行時は未取得の四半期だけを取りに行く。

## 6. データクレンジング
- 価格・面積・延床・建築年が数値として解釈できないレコードは除外する（「戦前」、「2000㎡以上」のような上限表記など）。除外件数は理由別に集計する。
- 備考欄に関係者間取引など特殊事情を示す記載があるレコードは除外する。除外ルールは `config/exclusion_rules.json` で管理する。
- ㎡単価の外れ値は、市区ごとにIQR法で除外する。
- 取引価格（01）と成約価格（02）でフィールドの充足状況が異なる可能性がある。**まず両者のフィールド充足率をレポートし、どのモデル工程でどちらを使うかを `docs/decisions.md` に記録してから進める。**

## 7. 査定ロジック（v1）

### 7.1 基本式
```
推定価格 = 土地価格 + 建物価格
土地価格 = 町名別の土地㎡単価 × 土地面積
建物価格 = 延床面積 × 再調達単価 × 残存率(築年数)
残存率   = max(下限値, 1 − 築年数 / 耐用年数)
```
- 再調達単価・耐用年数・残存率の下限値は `config/model_params.json` で管理する（初期値は木造を想定した仮の値とし、7.3の補正で吸収する）。

### 7.2 土地㎡単価の推定（フォールバック階層）
1. 町名：直近3年の土地取引が N件以上ある → 中央値を使う
2. 市区：1を満たさない → 市区の中央値を使い、`confidence = low` のフラグを立てる
3. 市区でも件数不足 → 価格を出さない（`confidence = none`）

- Nの初期値は10（設定値）。時点の補正（地価の変動）は、市区ごとの四半期別中央値の推移から年率で補正する。

### 7.3 補正
- 戸建て取引データに7.1の式を当てはめ、市区ごとに「実際の価格 ÷ 推定価格」の比率分布を求める。
- 比率の中央値を補正係数として推定価格に掛ける。
- 比率の25〜75パーセンタイルをレンジの幅として使う（`confidence = low` のときは10〜90パーセンタイル）。
- 余力があれば v1.1 として、駅徒歩分数・土地面積・築年数を説明変数に加えた対数線形回帰を実装し、7.3の比率方式とバックテストで比較する。

### 7.4 出力
- 価格レンジ（下限〜上限）、10万円単位で丸める
- 根拠データの件数、データの対象期間
- confidenceフラグ

## 8. 入力仕様（UI）

| 項目 | 必須 | 備考 |
|---|---|---|
| 市区 | ○ | `config/areas.json` の有効エリアのみ表示 |
| 町名 | ○ | 選択した市区の町名一覧（データ由来）から選ぶ。「わからない／一覧にない」を選ぶと市区単位で計算 |
| 築年 | ○ | 西暦または和暦。「だいたい」でよいことを明記する |
| 土地面積 | 任意 | ㎡または坪。未入力時はその町名の中央値で計算し、レンジを広げる |
| 延床面積 | 任意 | 同上 |
| 最寄駅徒歩 | 任意 | v1.1の回帰で使用 |

- 入力ステップは最大3画面。スマホファーストで設計する（主要な流入はスマホを想定）。
- 未入力の項目があった場合は、結果画面に「○○は標準値で計算しています」と表示する。

## 9. 結果画面の仕様
- 価格レンジを大きく表示する。単一の価格は表示しない。
- 根拠の要約を表示する（例：「中央区○○町周辺の取引データ○件をもとに推定」）。
- 注意書き：
  - 公開データにもとづく参考価格であり、査定書・鑑定評価ではない旨
  - 接道、土地の形、リフォーム歴、再建築の可否などは反映されていない旨
- CTA：「接道や土地の形で価格は大きく変わります。担当者が無料で精密査定します」→ 既存の査定フォームへ遷移する。遷移時は物件情報（市区・町名・築年・面積）のみをパラメータで引き継ぎ、個人情報は扱わない。
- `confidence = none` の場合は価格を出さず、「このエリアは担当者が個別に査定します」と表示してCTAへ誘導する。
- **クレジット表示**：不動産情報ライブラリの利用規約で定められた出典・免責文言を、規約の記載どおりに表示する（文言は規約から正確に転記すること）。
- 表示ルール：「最高値」「必ず高く売れる」など、断定・最上級の表現は使わない（不動産の表示に関する公正競争規約に配慮）。

## 10. 計測
- GA4のカスタムイベントを送信する：`satei_start`（入力開始）、`satei_step`（ステップ遷移）、`satei_result`（結果表示：confidenceを含む）、`satei_cta_click`（CTAクリック）。
- GA4の測定IDは設定値にし、未設定でも動作すること。

## 11. バックテスト
- 直近4四半期の戸建て取引をテストデータとして除外し、それ以前のデータでモデルを作って予測する。
- 指標：MAPE、±10%以内の割合、±20%以内の割合、レンジ内に入った割合。いずれも市区別と全体で算出する。
- 出力：`reports/backtest.md`
- 自社の成約データでも検証できるよう、CSVの入力フォーマット（市区コード、町名、成約価格、土地面積、延床面積、築年、成約年月）を定義し、同じ指標で評価するスクリプトを用意する。

## 12. 開発フェーズ

| フェーズ | 内容 | APIキー |
|---|---|---|
| Phase 0 | リポジトリ構成、設定ファイル、査定ロジック、UI、テスト。テストは**明示的にテスト用と分かるfixture**で行う | 不要 |
| Phase 1 | データ取得、クレンジング、データプロファイル（市区×町名別の件数、フィールド充足率）を `reports/data_profile.md` に出力 | 必要 |
| Phase 2 | モデル推定、`model.json` の生成、バックテスト | 必要 |
| Phase 3 | Netlifyへのデプロイ、GA4設定、四半期更新のGitHub Actions化 | 必要 |

- **fixtureの数値を本番の model.json や画面表示に流用しないこと。** Phase 1が終わるまで、UIのプレビューには「サンプルデータ」と明示した表示を出す。
- 各フェーズの終了時に、成果物と判断事項をまとめて報告し、承認を得てから次へ進む。

## 13. 未決事項（実装は初期値で進め、設定で変更できるようにする）

| 項目 | 初期値 | 決定者 |
|---|---|---|
| 稲毛区を対象に含めるか | 含めない（無効） | プロモーション戦略課 |
| ツールの名称 | 「かんたん相場査定」（仮） | 同上 |
| 既存の査定フォームのURL | 設定値（未設定時はダミー） | 同上 |
| 公開判定の合格基準 | ±20%以内の割合が60%以上（仮） | 同上 |
| 結果表示前に連絡先を求めるか（ゲーティング） | 求めない | 同上 |
| 町名単位で計算する最低件数N | 10 | Phase 1のデータプロファイルを見て決める |

## 14. 受け入れ条件
- [ ] 実行時に外部APIへのリクエストが発生しない（ブラウザの開発者ツールで確認）
- [ ] APIキーがリポジトリと公開ファイルのどこにも含まれていない
- [ ] 有効な全エリアで、町名ありと町名なしの両方のケースで結果が表示される
- [ ] 件数が不足しているケースで価格が表示されず、CTAに誘導される
- [ ] クレジット表示と注意書きが結果画面に表示されている
- [ ] バックテストのレポートが出力され、合格基準を満たしている
- [ ] スマホ（幅375px）で表示崩れがない
- [ ] 四半期更新のワークフローが手動実行で成功する
